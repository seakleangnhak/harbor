## Memory model and current operating guidance

The unchanged production geometry is 100 MiB authenticated storage chunks,
4 MiB browser parts, two pending chunks/upload, four globally, one saving worker,
two large-chunk engine slots, and a two-entry ciphertext cache capped at 256 MiB
including reservations. No concurrency or encryption-format change is proposed.

Each active chunk needs its whole envelope before authenticated plaintext can
be served. Cache hits allocate a private ciphertext buffer and authenticate it
in place; disk cache is not a persistent plaintext cache. Cached files, encrypted
staging, local fixture blobs and SQLite/WAL also occupy reclaimable kernel page
cache. Go's soft limit excludes kernel page cache and is not a total container
memory cap. Cached file pages can make `memory.current` reach a hard limit while
anonymous/live memory remains lower; reclaim pressure and stall measurements
matter alongside OOM counters.

Milestone B's approximately 89-second fixture measured lifetime RSS 520.05 MiB,
last-GC live heap peak 208.84 MiB, cgroup peak 770.00 MiB and 248,698
`memory.max` events under the configured 768 MiB limit. OOM counts were zero.
These are prior measurements, **not** the new extended qualification. They prove
neither spare cgroup margin nor comfortable live-Telegram mixed capacity.

Keep `GOMEMLIMIT=512MiB` and existing worker/queue/cache bounds for this candidate.
768 MiB is a constrained qualified fixture configuration after its 30-minute
soak, not a claim of spare capacity or comfortable sustained live-Telegram
headroom. The fresh 1024 MiB comparison observes lower reclaim stalls while
anonymous/live memory stays similar. A separately configured 1 GiB hard budget
with the same 512 MiB Go limit is a tested optional operating point when reclaim
latency matters. It is the smallest conventional next budget tested, not a
search for the mathematical minimum. It still reaches its hard ceiling through
file cache; no spare cgroup-memory margin is demonstrated there either.
No production limit, owner deployment or concurrency is changed.

For an installation under pressure, monitor cgroup `memory.current`, the `anon`
and `file` fields in `memory.stat`, `memory.events`, and `memory.pressure` (PSI).
Compare cumulative PSI stall-time deltas over a known interval; one instant's
`avg10` is not a whole-run measurement. `docker stats` working set is not process
RSS. Investigate any OOM/kill event, integrity failure, job without progress or
rising anonymous/live memory after work drains. High reclaim counts with stable
live memory and completed work require latency/PSI review, not an automatic
concurrency or memory increase. The controlled 1024 MiB comparison below retains
the same 512 MiB Go limit, source and workload. Its extra page cache does not
establish application-memory headroom or fix a leak. Actual installation guidance
still depends on its workload, latency targets and measured pressure.

Every five-minute window makes upload/download progress. Window live-heap peaks
rise from 208.87 to 209.38 MiB at 768 MiB and from 208.83 to 209.37 MiB at
1024 MiB; both settle near 1 MiB after explicit GC. The harness retains samples
and latency slices, so small drift cannot be attributed to application retention
without profiles. Cumulative allocations measure churn across unequal operation
counts, not retained memory or an equal-work per-operation comparison.
CPU includes in-process clients, hashing and sampling. Brief CPU accounting can
exceed the two-CPU quota over a sampling window. Peaks of distinct memory fields
occur at different times and must not be summed; Go system/reserved heap is not
resident memory.

The cgroups reach both hard ceilings. Matched roughly 300-to-1800-second passive
captures show:

| --- | ---: | ---: |
| Observed interval | 1500.197 s | 1499.809 s |
| Full memory-PSI stall-time increase | 30.377 s | 14.094 s |

| Page scans / page steals increase | 296749632 / 296744638 | 147954304 / 147949362 |
| File-page refault increase | 182032517 | 107279324 |

These are page-reclaim counters, not measured physical-disk bytes. Initial
passive captures happened about 126/21 seconds after startup, so they are not
matched idle baselines. Full PSI is evaluated over the later matched windows.
Kernel peaks can transiently exceed configured limits by small accounting
amounts. More file cache and fewer observed stalls at 1024 MiB do not prove a
general performance gain, lower application retention or spare memory. Fixed
order, one sample per budget and other isolated tasks sharing the physical host
limit causal comparisons. No unbounded retained heap/staging/cache growth,
unexplained large disk accumulation or deadlock was observed within either run.

Retained disk follows the six copies and source fixtures; final logical bytes
are identical. The durable restart here reconstructs the engine in-process
after workers/readers join; it is not a process-kill test. Process interruption
is covered by the separate tests above and the live controller. Synthetic range
requests are not real PDF/video rendering or Telegram wire traffic. See the
[soak report](V1.3_SOAK_REPORT.md) for exact source/binary manifests, latency
percentiles, local adapter counters and limitations.

The focused tests bound disposable scratch, but production persistent volumes
have no application-wide disk quota. Retain free capacity for encrypted pending
parts, 256 MiB cache reservations, SQLite/WAL and independent encrypted archives.
Maintenance is offline and confirmed; unknown or recoverable artifacts and all
remote messages remain preserved. Restore into a fresh destination; never clean
an active installation or infer remote abandonment from age alone.

Four fresh 100 MiB pending chunks can require approximately 400 MiB of encrypted
staging payload, plus envelope/filesystem overhead. Add the 256 MiB cache ceiling,
in-flight part writes, SQLite/WAL, retained recoverable or unknown artifacts, the
actual local library when using the local adapter, and backup space. This is a
planning model, **not a total disk bound or production quota**. Older retained
artifacts can outlive active queue slots. Alert on declining free space and
staging that fails to drain; use offline diagnostics before any confirmed cleanup.

## Scope limits

These fixtures do not qualify physical power loss, full host-disk failure,
multi-day workload, independent security auditing or provider durability.
Actual ENOSPC was injected into the separate staging filesystem, not the whole
database/host volume; SQLite failure used a controlled abort separately.
Default/tagged/race/vet suites, exact-image graceful shutdown/restart, live
Telegram, browser media, upgrade and archive rollback have separate ledgers.
Application RSS is distinct from whole-container cgroup memory and from Go
heap. In-process generated clients and samplers count toward fixture RSS/CPU;
their measurements cannot be relabeled as standalone deployed-server memory.
