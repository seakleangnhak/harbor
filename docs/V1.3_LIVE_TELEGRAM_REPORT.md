## Controller and safety boundary

`scripts/milestone_c_live_check.py` uses immutable local image IDs, a fresh
protected fixture volume and the separately authorized local test account. It
holds the source drive's exclusive lock until target containers stop, copied
session files are removed, the complete generated restore and encrypted
archive/password volumes are destroyed and private host runtime files are removed.
It never copies the source metadata database, content key or owner password.
It never deletes Telegram messages. Generated remote fixture references remain
in protected new metadata volumes after authorization removal.

The exact image runs as UID/GID 65532 with a read-only root, all capabilities
dropped, no new privileges, two CPUs, 128 PIDs, 768 MiB hard memory/no swap and a
512 MiB Go soft limit. Only this live fixture receives external networking and
runtime credentials. HTTP is published on a random loopback-only host port.
Application secrets never enter build arguments, source snapshots or image cache.

Default live interval is a real 900 seconds after candidate upgrade readiness;
optional intervals are bounded to 900–1800 seconds. The completed RC process
loaded the earlier controller with a 60-second cycle target and performed 14
paced cycles. The next-run controller uses a minimum 180-second cycle target
(about five cycles in 900 seconds), reducing cumulative traffic across RC and
final-image qualification. Multipart, concurrent, interruption, restart,
recreation, backup and restore checks remain unchanged.
Report distinguishes interval duration, per-cycle active time, startup/restart
and recovery time. This is a bounded reliability session, not a continuous
maximum-throughput or multi-hour live capacity test.

## Workload

- Optional v1.2.1 image seeds a generated 1 MiB file, stops cleanly, creates and
  verifies an encrypted pre-upgrade archive, then upgrades the same fixture
  installation to the candidate. File SHA-256 and session reconnection must pass.
- Candidate accepts a generated 5 MiB file in two transport parts (4 MiB and 1 MiB). Actual
  SIGKILL occurs only after observing `storing`. Restart must recover accepted
  parts automatically, retain unpublished state until verification, and produce
  the expected full digest. This does not identify an exact MTProto wire offset.
- Container recreation preserves session, completed manifests and HTTP ranges.
- Generated 100 MiB + 17-byte multipart file uses two unchanged storage chunks;
  background completion, full download and SHA-256 must pass.
- Three separate authenticated clients concurrently upload 1 MiB files through
  the one bounded saving worker, followed by checksum downloads.
- Paced cycles upload/download 1 MiB fixtures and read repeated overlapping
  64 KiB ranges of the large file. Timings are HTTP measurements; first range
  is not automatically classified as a cold remote cache miss.
- Post-run encrypted backup is verified and restored into a fresh directory.
  Restored startup obtains Telegram configuration, key and session from the
  archive, then verifies the large file's full SHA-256. Original configuration
  values are removed from the supplied runtime environment for this check.
  The first RC run still mounted the generated source `/live` volume during
  restored startup; archive-only mount isolation was not demonstrated in that
  run. The next-run controller removes this mount, inspects actual Docker mounts
  before startup and records `archive_only_mount_proofs`. Recovery one-shots
  retain mounts needed to create and restore the archives.
- With the optional old image, pre-upgrade archive restores into a separate fresh
  directory. v1.2.1 must reconnect and read its original file, while newer file
  references remain preserved in the stopped candidate fixture installation.

## Traffic accounting

Controller reserves conservative application encrypted-payload bounds before
operations: at most 1.5 GiB uploaded and 4 GiB downloaded, below the owner's
2 GiB/5 GiB budgets. Reservations include full storage envelopes for tiny ranges,
remote completion verification, an extra possible interrupted upload and fresh
restore downloads. Reservations are synchronized across upload clients.

Native MTProto retransmission/RPC wire bytes are not individually instrumented.
Docker network samples provide a second conservative safety stop at 1.75 GiB TX
or 4.5 GiB RX, including local HTTP traffic. Sampling is not a packet-exact cap.
Any observed transport retry count/disconnected state stops further workload;
no intentional rate limit or automatic retry storm is attempted. A triggered
network safety stop prevents PASS.
