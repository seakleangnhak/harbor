# v1.3 sustained-workload qualification

Date: 2026-10-22. Status: **PASS for two independent 30-minute generated local
workload intervals**, first at 768 MiB and then at 1024 MiB. These are not a
continuous 60-minute soak. Overall release acceptance is recorded separately in
[Final gate](V1.3_RELEASE_FINAL_GATE.md).

## Scope and reproducibility

The fixture executes real authenticated HTTP upload/download/range endpoints,
encrypted staging, the durable saving worker, final remote verification and
folder-copy workers. Its backend is a delayed **local ciphertext adapter**:
25 ms before each read, 75 ms before each write. It is not a Telegram benchmark.
Its two range clients retrieve synthetic `.bin` ranges; they do not establish
PDF rendering or video playback performance. Browser and live Telegram
qualification are separate workstreams.

```sh
python3 scripts/milestone_c_soak_check.py --minutes 30 --run 1
python3 scripts/milestone_c_soak_check.py --minutes 30 --memory-mib 1024 --run 1
python3 scripts/milestone_c_soak_test.py
```

Harness checkpoint: `e0efbf7`. Both generated build contexts contain identical
SHA-256 allowlists for 64 internal Go/module files. Both produce the identical
linux/arm64 API test binary:

```text
c1cd115fba3913171e283234fa506d3e4dca45091658162fceeeb0696f1b1f48
```

These are test-harness images and binaries, not the final Harbor release image.
Source hashes, binary hashes, build/runtime logs, one-second samples, final
integrity reports, five-minute summaries and passive cgroup captures remain in
ignored `output/milestone-c/soak/{30m-1,30m-1024m-1}/`. No runtime credentials,
owner databases, Telegram sessions, keys or private archives enter these
contexts. Generated fixture containers/volumes are removed by each controller.

The two stdlib soak-report tests reject unsafe/incomplete evidence and verify
observed-time CPU windows. They passed in the final isolated 72-test Python

## Workload and acceptance assertions

Each independent run creates three 100 MiB encrypted sources and performs two
sequential uploads. Its mixed interval runs two uploading clients, one full
100 MiB HTTP downloader and two overlapping/end-of-chunk 256 KiB range clients.
Six durable 300 MiB folder copies start at five-minute intervals. Each newly
uploaded mixed fixture passes normal remote verification/publication, then is
recycled through the real Trash/permanent-delete APIs to bound retained disk.
Only generated local fixture objects are deleted.

After 1800 seconds the test joins active readers/writers, accepts a pending
encrypted upload, reconstructs the storage engine/worker, drains that queued
work and runs another 15 seconds of range/cache pressure. This is an **in-process
engine restart**, not a SIGKILL or container-restart qualification. Separate
resource/live tests cover process and container interruption.

The fixture independently reopens/hashes 22 retained files: three sources,
one resumed upload and 18 copied files. Two earlier sequential uploads already
passed normal remote final verification. It requires zero metadata-integrity
issues/suppressed issues, no incomplete visible manifest, no OOM events/kills,
no pending/staged rows at settlement and exactly one simultaneous remote saver.
The report validator requires transfer progress in every five-minute window.
One-second publication sampling supplements transition/concurrency tests; it
cannot prove every transient interleaving by itself.

All six five-minute windows in each run contain completed uploads/downloads.
Window live-heap peaks rise from 208.87 to 209.38 MiB at 768 MiB and from 208.83
to 209.37 MiB at 1024 MiB, while RSS peaks remain bounded and final live heap
settles after GC. The harness retains sample/latency slices;
small live-heap drift must not be attributed to application retention without
profiles. Expected library growth follows the six retained copies, followed by
the one resumed file. Final 24 x 100 MiB source/file ciphertext plus 200 MiB cache
accounts for most of the 2604.16 MiB retained fixture; metadata/WAL account for
the remainder. Final disk bytes are identical in both runs. No unbounded
staging/cache growth or unexplained large disk accumulation was observed within
these intervals. Peak fields occur at different instants and must not be added.
Cumulative allocation measures allocation churn over unequal amounts of work,
not retained memory or an equal-work per-operation comparison. One-second CPU
accounting can briefly exceed the two-CPU quota because of scheduling windows.

The 768 MiB cgroup repeatedly reaches its hard ceiling. Between the 300.42 s and
1800.61 s passive captures, full memory-PSI stall time increases by 30.377 s over
1500.197 s (**2.025%**). Page scans/steals increase by approximately 296.75 million
pages; file refaults by 182.03 million pages. These are reclaim counters, not
measured physical-disk bytes. Zero OOM events do **not** establish spare cgroup
memory or an operationally comfortable margin. Kernel accounting permits a
small transient peak above configured `memory.max`.

minimum. No production configuration is changed.

## Limitations

These are two independent 30-minute intervals, **not one continuous 60-minute
soak**. Fixed order and shared physical-host contention from other isolated
qualification tasks limit causal throughput comparisons. One sample per budget
cannot establish general speed or memory improvements. No changes to production
resource limits, encryption format, queue bounds or concurrency are made here.
Longer unattended durations, sustained live Telegram resource headroom and
other hardware remain separately unverified. The fixture's disk assertions are
not production quotas; `HeapAlloc`, live heap, reserved heap, process RSS and
cgroup/page-cache accounting measure different things and must not be added.
