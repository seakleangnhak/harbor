# Harbor Phase 3 performance qualification

Date: 2026-10-21 (Asia/Phnom_Penh).

Status: **PASS for controlled performance measurements**. Real Telegram baseline/optimized uploads and downloads passed SHA-256 verification at 1, 10 and 100 MiB. Synthetic before/after engine and MTProto benchmarks passed. Numbers describe measured runs, not sustained service guarantees; broader acceptance is tracked in [Phase 3 final report](PHASE3_FINAL_REPORT.md).

## Workload and measurement boundaries

Coordinator ran generated deterministic 1, 10 and 100 MiB fixtures through authenticated Harbor HTTP against real Telegram. One HTTP transfer at a time, 4 MiB application chunks, engine ceiling four operations. No account stress or deliberate live rate-limit trigger. Existing keys, SQLite and dedicated account session retained. Qualification objects remain tracked; no preexisting messages deleted.

Upload time covers upload creation, chunk requests, local harness state writes and server completion. Completion reads all remote chunks again to authenticate and verify whole-file SHA-256 before publication. Client fixture digest generation precedes upload timing. Download time covers HTTP streaming, exact generated-byte comparison and SHA-256. Thus figures measure Harbor API behavior, not isolated MTProto wire bandwidth. Client buffers one application chunk for upload and 256 KiB blocks for download; file size does not determine client download memory.

Baseline used the existing Phase 2 executable. Optimized comparison uses rebuilt Phase 3 code with the same host, account/channel, data directory, 8081 loopback port and default Go GC. Runs occur sequentially; Telegram/network conditions can vary. One observation per size is qualification evidence, not statistical capacity prediction.

Real 512 MiB workload: **NOT TESTED**, intentionally omitted to keep account traffic controlled after 1/10/100 MiB measurements. A separate local 512 MiB streaming/integrity check passed below; local throughput cannot qualify Telegram performance.

## Measured changes

### MTProto upload part size

Installed gotd/td v0.162.0 defaults to 128 KiB upload parts. Its small-file upload loop is sequential for documents below 10 MiB, including Harbor's default encrypted 4 MiB chunks. `WithThreads(2)` therefore does not create two simultaneous part requests for these chunks. Raising only part size to 512 KiB reduces a 4 MiB + 32-byte encrypted envelope from 33 to nine part RPCs on a successful first attempt. A 1 MiB + 32-byte envelope drops from nine to three RPCs. These counts exclude retries and document-publication RPCs. This reduces request overhead without raising request concurrency.

Synthetic measurements use the real gotd uploader with an intercepted in-memory RPC invoker on Apple M3 Pro, darwin/arm64. No Telegram connection/session. `GOGC=40`, benchmark duration 100 ms. Simulated latency is one millisecond per RPC; values are measured synthetic results, **not live Telegram bandwidth**.

| Payload | Part size | RPCs/upload | No-delay milliseconds | No-delay B/op | No-delay allocs/op | With 1 ms RPC delay, milliseconds |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 MiB + 32 bytes | 128 KiB | 9 | 1.294436 | 134,288 | 62 | 12.121194 |
| 1 MiB + 32 bytes | 512 KiB | 3 | 1.323407 | 527,095 | 33 | 5.044108 |
| 4 MiB + 32 bytes | 128 KiB | 33 | 5.470040 | 136,449 | 182 | 43.652944 |
| 4 MiB + 32 bytes | 512 KiB | 9 | 5.262850 | 527,592 | 62 | 16.651042 |

At controlled 1 ms latency full-chunk elapsed time fell from 43.65 to 16.65 ms (61.86% lower) with 512 KiB parts. Additional uploader buffer allocation is approximately 382 KiB per active upload. Immediate no-delay CPU results were similar; request reduction is the rationale. Tests verify production `Put` uses ordered 512 KiB parts with exact tail bytes, keeps send identity across transient retries, and never sends an incomplete document after cancellation. A separate reconstruction test verifies exact bytes and Telegram's small-file MD5 protocol checksum; content security remains AES-GCM and SHA-256.

Synthetic pre-change document download of 4 MiB + 32 bytes took 0.473102 ms, allocated 4,205,791 B/op and 87 allocs/op. It used pre-sized ciphertext buffering with no whole-file copy. No download concurrency/cache layer was added to the adapter on this evidence.

Flood-wait telemetry now marks the state before gotd sleeps; native completion callback skips an already-counted flood event. Controlled tests verify long-wait cancellation and one count after a completed short wait. No custom retry loop or request concurrency increase.

### Engine allocation and HTTP preflight

Synthetic engine benchmarks use temporary SQLite, authenticated encryption and a cloning in-memory blob adapter. Figures below are medians of three runs, ten iterations each, on Apple M3 Pro. Commands have no explicit GC/GOMAXPROCS override; benchmark output reports 11 processors. These allocations are cumulative B/op, **not peak process RAM**, and throughput is not Telegram throughput.

| 4 MiB operation | Before milliseconds | After milliseconds | Before B/op | After B/op | Latency reduction |
| --- | ---: | ---: | ---: | ---: | ---: |
| Put chunk | 3.135796 | 2.439158 | 18,405,691 | 12,613,976 | 22.22% |
| Authenticate/decrypt chunk | 2.097967 | 2.096717 | 8,398,161 | 8,398,007 | 0.06% |
| Stream chunk | 2.308675 | 2.191788 | 8,403,959 | 8,402,894 | 5.06% |
| `http.ServeContent` | 4.233646 | 2.200583 | 16,808,899 | 8,407,034 | 48.02% |

Before: unchanged Phase 2 engine/reader. After: bounded plaintext input preallocation, a single pre-sized AES-GCM envelope with fresh random nonce, retained cached chunk across `http.ServeContent` preflight seeks, failed-fetch cache invalidation and upload-status geometry guard. API/blob contracts and four-slot concurrency ceiling unchanged. No plaintext in-place decryption.

Put allocation fell 31.47%; `ServeContent` allocation fell 49.98%. A correctness regression separately proves first encrypted chunk is fetched once rather than twice across the HTTP preflight sequence. Measurements support retaining that one cached authenticated chunk; no file-wide cache was introduced.

Evidence: `output/phase3/engine-baseline.txt`, `output/phase3/engine-optimized.txt`.
