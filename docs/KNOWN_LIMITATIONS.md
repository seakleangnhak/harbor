# Harbor v1.0 known limitations

Scope: single owner on a trusted local host. Release acceptance, exact image identity and fresh test results are recorded in the [Phase 6 report](PHASE6_FINAL_REPORT.md) and [release checklist](RELEASE_CHECKLIST.md). Historical results describe their own tested source/image, not every later build. Local personal-use qualification does not establish independent security audit, public internet readiness, guaranteed Telegram durability, or universal accessibility/browser compatibility.

## Storage and recovery

| Boundary | Current behavior and operator action |
| --- | --- |
| Live cross-datacenter retrieval | **NOT TESTED.** No legitimate, safe known-other-DC fixture was reproduced. gotd v0.162.0 primary routing handles authorized DC migration. Harbor's secondary-media `FILE_MIGRATE` fallback now hands off once to that primary route; deterministic tests cover exact bytes/location, cancellation, terminal errors and expired-reference reconstruction. This is simulated/source coverage, not live placement evidence. |
| Telegram dependency | Account restriction, channel deletion, changed permissions/retention or lost messages can make content unavailable. Use a dedicated account and owned private channel with auto-delete disabled. Harbor cannot guarantee provider durability or recover missing ciphertext from metadata. |
| Telegram retry bounds | Blob operations have a two-minute context and at most six **outer** attempts, with terminal-error rejection, bounded backoff and FLOOD_WAIT cancellation. gotd uploader/downloader/native migration can perform additional RPCs within that deadline; six outer attempts is not a six-wire-request guarantee. Retry counters are process-local telemetry, not a durable per-RPC audit. Real rate restrictions/session revocation are not deliberately induced. |
| Recovery archive contents | Telegram archives preserve local DB, key, binding, allowlisted config, session and ordered references; remote encrypted files remain in Telegram. Local-adapter archives also contain referenced ciphertext. Keep an independent encrypted off-provider content copy for provider loss; Harbor does not create that mirror. |
| Backup scale | Offline backup only. SQLite snapshot at most 256 MiB, each manifest at most 64 MiB, at most 250,000 members and 1 TiB uncompressed payload. Snapshot stays in RAM and peak use can exceed twice DB size; ceiling-scale resource use is unqualified. No automatic scheduler, retention, off-host copying or key escrow. |
| Recovery failures | Destination must be nonexistent; no in-place overwrite/repair. Wrong passwords/corruption fail closed. SIGKILL/power loss may leave private unpublished staging requiring careful operator cleanup. A saved owner password is optional; otherwise owner must know it. A saved Telegram authorization may still be expired/revoked. See [quickstart](RECOVERY_QUICKSTART.md). |
| Folder-copy bounds | Durable jobs accept at most 100 selected roots, 10,000 planned entries, destination-inclusive depth 512 and eight unfinished jobs. One worker processes bounded chunks serially; metadata appears after whole-tree verification. Source names/hierarchy/favorites are captured, but source content must remain accessible. A 10,000-entry success is a code ceiling, not a qualified performance promise. |
| Copy cancellation/conflicts | Cancellation cleans generated staging; failed cleanup remains recoverable through explicit retry. Name/destination conflicts can require owner intervention. File-only browser copies use the existing transfer queue; they do not become one atomic tree transaction. Originals remain intact. |
| Orphans and repair | A crash between remote ciphertext creation and SQLite commit can leave orphan messages. No automatic remote garbage collector or metadata repair exists. Local orphan candidates are review-only library output. Never delete messages broadly or initialize a damaged bound installation. |
| Integrity commands | `integrity` checks metadata without fetching blobs, but Telegram CLI startup still requires adapter connectivity. `integrity-content` reads whole files serially and may create substantial Telegram traffic. Neither repairs/deletes data. Health/readiness are minimal liveness/DB/cached-transport checks, not full file or channel-durability checks. |
| Upgrade/rollback | Quiesce jobs, stop sole instance and verify encrypted backup first. Additive Phase 4↔v1.0 rollback was qualified on generated local-adapter data; arbitrary future downgrades are unsupported and newer schema versions reject startup. Legacy Docker volume roots may need documented offline 0700 permission migration. Never remove persistent volumes during upgrade. |

## Security and deployment

| Boundary | Current behavior and operator action |
| --- | --- |
| Host trust | Protected files/parents isolate other local accounts, not the same OS user, root, hostile filesystem or offline disk theft. Metadata names, sizes, MIME and hashes remain plaintext in private SQLite; active keys/sessions exist on host. Use disk encryption and separate encrypted recovery copies. |
| Key/session lifecycle | No in-place content-key rotation/re-encryption command, owner-password rotation UI, or global HTTP session-revocation UI. Replacing content key breaks existing decryption. Revoke stolen Telegram authorization through trusted Telegram Devices, reauthenticate locally, then replace affected recovery archives. |
| Owner sessions/throttle | HttpOnly host-only SameSite=Strict cookie, fixed seven-day expiry and server-side hashed tokens. Logout revokes current token; expiry is not sliding. Login throttle is process-local, resets on restart and counts successful attempts too: eight attempts per actual peer per 15 minutes, bounded peer map. Reverse-proxy clients share proxy peer; untrusted forwarding headers are ignored. |
| Network scope | Default host binding is localhost. Compose opts into its container-internal HTTP listener while publishing loopback only. Secure-cookie configuration does not provide TLS. Deliberate remote access requires a tested HTTPS reverse proxy and preserved same-origin/Range/streaming behavior; no public deployment or external penetration test was performed. |
| Authorization copies | Original and restored/cloned MTProto authorizations must run serially. Process locks protect one data directory; different copied directories alone cannot enforce this. Qualification harnesses hold original lock, but failure/SIGKILL still requires explicit no-clone verification before original resumes. |

## Browser and interaction scope

| Boundary | Current behavior and operator action |
| --- | --- |
| Download progress/integrity | Managed downloads at most 32 MiB use bounded browser verification before saving. Larger files use native browser downloads; Harbor cannot observe their progress/completion, pause/resume or independently hash saved bytes in the transfer panel. Backend still verifies authenticated chunks and supports byte ranges. Compare saved SHA-256 for external verification. |
| Transfer persistence | Upload reload requires reselecting original file; confirmed server chunks remain reusable. Managed-download resume starts again from byte zero. Browser queue allows 1,000 pending transfers with bounded completed history; browser storage can be cleared or unavailable. Server folder jobs persist separately. |
| Previews | Text/code preview shows first 256 KiB with modest token highlighting. Audio/video playback and seeking depend on browser codec support. PDF/image viewers are previews, not editors; unsupported formats require download. Large-directory virtualization does not eliminate metadata-query, response or browser-memory cost at unqualified scales. |
| Browser/accessibility coverage | Automated Chromium and WebKit plus emulated mobile are the main coverage. WebKit engine testing is not actual Safari/iOS or physical-device testing. Scoped axe/keyboard/layout checks do not establish universal WCAG or screen-reader certification. Long-duration browser-memory behavior and every codec/browser combination remain unqualified. |

Exact final-image live Telegram and archive-only fresh-volume recovery are required release gates. Their current outcomes belong in the Phase 6 report; neither earlier host authorization nor historical Docker tests substitute for those checks.
