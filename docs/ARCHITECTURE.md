# Architecture

Last verified: 2026-10-22. Product name: **Harbor** (Telegram Private Drive).

## Process and boundaries

Owner settings retain the single-owner model. An additive `owner_profile` singleton stores the display name and password-change timestamp; existing databases default to `Owner`. Authenticated profile updates return the existing session shape. Password changes verify the current password, enforce the existing 12–72 UTF-8 byte policy and atomically replace the bcrypt hash/revoke all sessions. Login issuance and password changes are serialized to prevent an old-password login surviving revocation. New plaintext passwords are never saved. SQLite's owner hash remains authoritative across restart; environment/setup password files are initialization inputs, not password-reset controls.

After a recorded password change, complete backups omit automatically discovered obsolete initialization-password files. The encrypted SQLite snapshot preserves the active hash and profile; restored users sign in with the owner password active at backup creation. An explicitly supplied recovery password file must still match the active hash. Older archives/databases without owner profiles retain their existing recovery behavior. No content key, stored file or Telegram authorization changes when an owner password changes.

Go/Chi modular monolith serves `/api/v1` and built React SPA on one origin. SQLite in WAL mode stores owner password hash, hashed revocable sessions, nodes and encrypted-content manifests. One DB connection serializes short SQL transactions; network I/O must happen outside transactions. No Redis, external job service, public sharing, signup, or remote URL ingestion. One joined in-process goroutine executes durable SQLite copy jobs.

`internal/api` owns auth, nodes, hierarchy validation, listing, trash, diagnostics and durable copy jobs. `internal/onboarding` owns token-guarded first-run account and Telegram authorization handlers. `internal/recovery` owns offline encrypted complete archives. `internal/storage` owns persistent upload sessions, chunk metadata, encryption, byte adapters and authenticated random-access readers. `internal/domain` defines shared DTOs; `cmd/drive` owns environment, DB/key lifecycle, first-run activation and adapter selection.

## Frontend workspace

Phase 4 retains React/TanStack Query/Virtual, Radix primitives and native CSS. Workspace coordinates server queries, metadata optimism/rollback, location preferences and internal clipboard. FileBrowser owns virtual selection/inline editing/internal drag; previews and transfer hook stay separate. Command palette/settings/PDF are lazy. Sidebar state and per-location view/sort preferences are browser-local. Menus are nonmodal; dialogs retain modal focus handling; scrollable PDF/transfer regions are keyboard-focusable. Themes apply before React mount.

First-run onboarding precedes the normal login/workspace. Its owner/storage/review flow holds the setup token and entered Telegram details only in component memory. QR images use authenticated no-store responses and data URIs; the browser rejects credential entry on remote plaintext HTTP. Successful completion clears inputs and polls readiness before enabling normal login. If startup takes too long, the UI reports saved setup and offers reload rather than resubmitting completion.

Individual browser file copy reads exact authenticated HTTP 206 ranges bounded to the application chunk, verifies total/hash headers and re-uploads through the encrypted engine. Folder-containing selections use persisted server jobs with immutable source metadata snapshots, ancestor pruning, 100 roots/10,000 entries/512 levels and eight unfinished jobs. A single worker stages fresh encrypted content serially using internal `copy:<job>:<entry>` parents. Per-chunk acknowledgements survive restart; indexed reconciliation closes the Begin-to-plan crash window. Internal stages cannot be listed or mutated through user upload routes. Publication inserts the complete hierarchy and completes the job in one metadata transaction after manifest checks. Concurrent source rename/move uses snapshot semantics; destination conflicts fail without partial visibility. Cancellation removes only job-created objects; cleanup failures wait for explicit retry. Original files are never removed by copy failure.

API schema migrations run transactionally with `PRAGMA user_version=1`; unknown future versions fail before migration. Shutdown joins HTTP draining and cancels/joins copy and upload workers before closing DB/transport. Browser copy-job polling refreshes completed locations and exposes persisted progress/retry/cancel; failed stages retain verified chunks. Browser managed file transfers still preserve 1,000 pending and 100 history entries in best-effort localStorage. Uploads need the original file after reload only for missing source bytes; fully accepted queued work resumes from server staging. Individual file copies resume verified chunks; managed downloads restart.

Image thumbnails default on with a persistent hide/show preference, raster size ≤8 MiB, viewport-aware loading and two concurrent original-image requests. Hiding thumbnails or leaving the listing cancels queued requests; video originals are never fetched for grid thumbnails. The nearby preview strip fetches at most five entries and only raster thumbnails ≤2 MiB. Text fetch/render caps at 256 KiB/2,000 syntax tokens. PDF renders one bounded canvas with demand Range fetching and standard fonts bundled locally. The packaged PDF.js compatibility build and matching worker support browsers missing newer JavaScript methods; accessible page text uses a cancellable stream reader capped at 256 Ki characters. Text extraction failure preserves the rendered page. The viewer remains lazy-loaded. Larger native downloads remain outside managed JS verification above 32 MiB. See Phase 4 reports for historical browser-only limits and measured bundle/DOM cost.

Preview routing normalizes declared MIME types and infers a fixed safe media type from the filename only when MIME is missing or generic. Content responses retain sandbox/nosniff, authorization, authenticated decryption and Range behavior; unsafe HTML/XML/SVG remain attachments. Images and native media expose loading, retry and original-download states. HEIC/HEIF and MOV use browser-native decoding; no transcoder or codec is bundled, so support depends on browser/device. Failed previews never modify stored bytes or metadata.

## Content model

New uploads use 100 MiB plaintext chunks; existing 4 MiB files and resumable uploads keep their persisted geometry. This does not impose a 100 MiB file cap: the existing API ceiling is 1 TiB. Each chunk is sealed independently with AES-256-GCM, random nonce and authenticated upload ID/index. Blob storage receives ciphertext only, with opaque names. Manifest records plaintext chunk SHA-256, size, blob reference and total SHA-256. At most a bounded number of chunks occupy memory; no whole-file buffering. Finalization reads/decrypts every chunk and verifies the whole file before metadata becomes visible. Download uses a seekable chunk reader, verifies each whole chunk before releasing its bytes and supports HTTP Range for video/PDF. Small previews/ranges can require fetching and authenticating up to 100 MiB first. Files are immutable after completion; rename/move changes metadata only.

Browser transport uses separate 4 MiB parts, up to 25 per default storage chunk. Each part has a required SHA-256, fresh AES-GCM nonce and transport-specific upload/chunk/part AAD, and persists encrypted under private `<data>/upload-parts` with `storage_parts` metadata. Two pending storage chunks per upload allow one to save while the next is sent; four global reservations bound active encrypted staging to about 400 MiB plus envelopes. Crash leftovers fall outside this window; a post-manifest cleanup error stops the worker/application, retaining tracked chunks for retry after restart. The opt-in background commit persists queue state before returning 202. One joined backend worker authenticates/decrypts staged parts in order into the existing bounded storage-chunk buffer, sends the unchanged encrypted chunk, and records its manifest before staging cleanup. It releases the short upload mutation lock during remote I/O, while a separate work lock protects commit/finalization/cancellation. Remote acknowledgement commits without reacquiring the browser-body lock; failure persistence uses a conditional `storing` update, so a slow next part cannot block either outcome or overwrite cancellation/requeue state. Storage plaintext remains 100 MiB maximum with unchanged 32-byte envelope. Legacy synchronous commit, whole-chunk clients and copy jobs remain supported.

Client XHR events measure bytes sent; acknowledgements measure durable local acceptance, and `received_bytes` remains committed remote storage. Additive pending-chunk status distinguishes receiving, queued, storing and failed. Sent progress cannot establish completion. Part/queue retries are bounded; capacity waits apply backpressure. Pause stops sending and leaves durable queued work running; reload reconciles server state and requires the original file only when bytes remain to send. Once a file is fully accepted and queued, the browser sender advances to the next file while one serial monitor reconciles saving and finalizes prior uploads. Backend restart recovers queued/interrupted saves. Staged files survive normal restart but are intentionally omitted from offline recovery archives; absent/corrupt parts must be resent. Cancel first persists intent, interrupts active saving, waits for its work lock, then removes tracked staged/remote chunks; failed cleanup remains retryable. No plaintext temporary upload files are created.

Plaintext input is bounded to expected chunk size plus one overflow byte. Upload sealing and download opening reuse their bounded chunk envelope in place. Persisted upload geometry is validated before division/allocation (chunk size 1 byte–100 MiB, nonnegative size and bounded chunk count). Readers retain one verified chunk across HTTP preflight/size seeks, then invalidate bytes/index before fetching another. Uploads, finalization and retained reader buffers share engine slots derived from a 256 MiB chunk-buffer budget, with at most four slots and two at the 100 MiB default. Part staging has a separate two-part buffer limit so a save and a preview cannot prevent the next 4 MiB part being accepted. A reader releases its slot when consumed/closed. This budget excludes other Go/transport allocations; container limits remain 512 MiB soft/768 MiB hard. Whole-file verification runs outside the API metadata-mutation lock; publication reacquires it and rechecks identity, destination and sibling conflicts.

Telegram seekable readers optionally reuse encrypted chunks through private `<data>/read-cache`, bounded to two entries/256 MiB including in-flight reservations. Concurrent misses for the same immutable manifest identity are coalesced. Each request still authenticates AES-GCM and checks SHA-256 before bytes are returned; cached ciphertext is never decrypted in shared buffers. Corrupt entries are evicted and fetched remotely once. Cache faults degrade to remote reads; it is disposable, omitted from recovery archives and not a content backup. Finalization and integrity auditing bypass it so they continue verifying actual adapter content. Cold preview/range latency still includes authenticating a complete stored chunk; repeated ranges can avoid remote fetches without changing encryption or browser `no-store` policy. The cache does not reduce per-reader full-chunk decryption allocations; eviction-heavy reads can be slower. See [cache qualification](CACHE_QUALIFICATION.md) for measured workload scope.

Upload IDs become file IDs. Client stores upload ID and file fingerprint; server persists received indices. Browser reload requires reselecting matching local files (browser security prevents silently reopening file handles). Retrying an identical chunk is idempotent; mismatched replacement is rejected. Finalization is idempotent, and API publishing recovers if process stops between storage completion and node insertion. Zero-byte files are supported. Trashing keeps content intact; permanent deletion durably marks subtree intent before byte removal. A failed/interrupted permanent deletion blocks restore and permits retry after restart.

## Authentication and deployment

Fresh installation requires a random 32–256-character `DRIVE_SETUP_TOKEN` supplied at runtime. The first-run server checks a SHA-256 token digest in constant time, expires setup access after one hour, bounds/rate-limits requests and applies same-origin checks. Public `GET /api/v1/setup/status` reveals only `{required:boolean}`. Protected endpoints accept the token in `X-Harbor-Setup-Token`; no token is accepted in a query string. Owner password must be 12–72 bytes without CR/LF. Setup cannot reopen when `drive.db`, `storage.json` or an activated setup bundle exists; legacy owner-file/environment initialization remains supported.

On completion, owner credentials and verified Telegram configuration/session are synced under private `setup.pending`, then activated together by an atomic rename to `<data>/setup`. Matching activation retries can finish a failed parent-directory sync without changing identity. Existing metadata prevents a new activation. The process then starts its normal key/storage/database lifecycle using the saved bundle. Process environment/private `.env` takes priority, and saved configuration fills unset values; conflicting explicit storage/password/Telegram settings reject new setup. Bundle directory mode is `0700`, secret files `0600`. An interrupted unfinished setup requires resubmission; its pending session cannot claim an initialized drive. The data lock is held throughout startup and authorization handoff.

Initialized owner passwords are stored as slow hashes in SQLite. Existing server-side secret file/environment deployments keep working. Login issues random opaque 256-bit cookie; SQLite keeps only token hash and expiration. Session cookie is HttpOnly, SameSite=Strict, Secure when configured. Mutations reject cross-origin requests; Go serves frontend so CORS is unnecessary. Login throttling and body limits constrain abuse. Bind loopback by default; Compose publishes loopback only. Use HTTPS and Secure cookies before any non-loopback deployment.

Content key is a random 32-byte file outside SQLite and Git. Private state requires 0700 directories/0600 secret files; SQLite DB/WAL/SHM are protected before opening. A storage binding records key fingerprint, adapter and Telegram channel ID. Existing missing DB/key/binding fails closed. Non-loopback HTTP requires explicit opt-in or HTTPS cookie policy; Compose keeps host publishing on loopback. `/health` reports process liveness, including during setup; `/ready` remains 503 until normal startup, then checks SQLite and cached Telegram connection without disclosing identities.

`harbor-recovery` takes the offline process lock, opens SQLite read-only and uses modernc supported Backup/Step/Commit/Serialize APIs into memory, including committed WAL. It writes no plaintext backup snapshot. Version 2 archives encrypt 1 MiB records with scrypt-derived AES-256-GCM, fresh salt, unique sequence nonces and header/order/length AAD; authenticated terminator and encrypted SHA-256 member manifest reject incomplete/corrupt archives. Complete archives include original key, allowlisted explicit runtime configuration, optional matching owner password, valid Telegram session, ordered chunk export, and referenced local blobs where applicable. Cap: 256 MiB metadata, 250,000 members, 1 TiB payload. Restore authenticates into private sibling staging, validates DB/materials, revokes restored web sessions, syncs files and publishes with OS no-replace rename. Original data is untouched. SIGKILL may leave unpublished private staging requiring operator cleanup.

Telegram backups preserve references, not an independent remote-content mirror. Account/channel loss requires an off-provider content copy. Copied MTProto authorization must run serially. `integrity` and `integrity-content` require existing state, audit metadata/content without deletion, and report bounded codes/opaque IDs. Local orphan candidates are review-only; no remote enumeration or automatic garbage collection. See Phase 5 operations and qualification reports.

Backup creation auto-detects `<data>/setup/config.env`, `owner-password` and `telegram.session` for browser-onboarded drives. Required materials enter the existing encrypted portable archive format; restore still emits its documented `recovery.env` and private root files. Explicit recovery input paths override detection and must describe the actual adapter. No plaintext setup archive or migration of existing archives is introduced.

## Telegram boundary

gotd/td implements MTProto blob storage; encrypted chunk documents map to channel messages. Fresh guarded web setup accepts API/channel details, exposes a temporary QR only to the setup-token holder, and relays a two-step password without saving it. The full session and saved API hash are never returned through HTTP. Legacy server-side terminal phone/code/2FA flows remain available. Setup/startup verify private owned channel and reject auto-delete retention. Owner must keep auto-delete disabled afterward. Flood waits/retries honor context cancellation. Local and Telegram adapters use the same encrypted engine, but data cannot switch backend implicitly. Real Telegram checks require a real dedicated account and are reported separately.

Setup, discovery and startup map typed Telegram, context and network errors to fixed safe categories and guidance. Classification never reads provider error text. Session-file presence does not establish authorization; startup checks account status before channel resolution. Telegram-app/SMS/voice-call OTP and two-step passwords use gotd's auth flow. An optional fixed-method callback supplies delivery guidance without phone/email patterns, codes, URLs or hashes. Unsupported email, caller-ID, Firebase and Fragment methods fail before asking for an ordinary code; no resend is issued.

Both web and terminal QR setup use gotd's native authorization with a three-minute network/approval deadline. A buffered login-update signal prevents losing approval during rendering; normal storage clients disable updates. The legacy `telegram-setup-qr` command renders locally in Terminal. Web setup instead encodes the callback URL as a private no-store PNG and waits for any two-step password through its protected endpoint. QR URLs/images never enter logs, persistent files or reports. Each explicit web authorization attempt resets only its pending session so a failed wrong-account attempt cannot silently reuse that account. Session persistence and target-channel guards are shared with OTP setup.

`USERNAME_OR_CHANNEL_LINK` or the web setup channel-link field selects an existing owned private channel by invite or private message link instead of manually supplied access hash. Optional channel ID verifies the resolved target before uploads; CLI and web input normalize Bot API IDs to positive MTProto IDs. A manual access hash cannot be combined with a link. Invite resolution uses read-only membership checks; no automatic joining/import occurs. Public usernames remain rejected. Startup resolves the selector within the existing authenticated MTProto connection, then checks the numeric channel ID against the immutable storage binding before opening SQLite or the content engine. Access hash remains server-side; no persistent resolver cache or access-hash browser exchange exists. Private-message links enumerate eligible normal/archived dialogs; an unrelated retention lookup failure currently blocks resolution rather than accepting an unverified channel.

gotd connection callbacks maintain cached `connecting`, `connected`, `retrying` and `disconnected` states. Authenticated diagnostics expose only state, timestamp and retry count. UI polls every five seconds without probing Telegram on each request. Chunk deadlines scale from two minutes with ciphertext size, adding one second per 256 KiB up to ten minutes. Application retries stop after six outer attempts, honor flood waits and cancellation, and refresh expired document references. Native gotd retry loops are deadline-bounded and can issue more than six wire requests. Download flood telemetry marks retry before native waiting and avoids duplicate counting. Telegram uploads use 512 KiB parts with a configured two-worker ceiling, including the multipart path for new 100 MiB documents. Interrupted parts restart the current application chunk while committed chunks resume from SQLite. Session replacement syncs file and containing directory.

Document downloads use the existing primary API when the document is in the current datacenter. Exporting authorization to the same datacenter fails with `DC_ID_INVALID`. Other datacenters use native media-only connections, closed after each operation. Both paths retain ciphertext-size limits, bounded context/retry, expired-reference refresh and engine AEAD/SHA-256 verification. Synthetic routing/bounds tests cover both paths; same-DC live retrieval is qualified separately.

gotd's primary invoker handles `FILE_MIGRATE` through cached authorized connections. A selected raw media pool returning `FILE_MIGRATE` now hands the same pending and subsequent reads back to that primary invoker once; native gotd handles target authorization/routing. Context, ciphertext bounds and reference refresh remain unchanged. Deterministic tests verify partial-read continuity, bounded fallback and cancellation. Actual live cross-datacenter placement/migration remains NOT TESTED. Phase 3 separately qualified real Telegram inside Docker, old-file retrieval, container recreation, partial-HTTP-upload SIGKILL and network detach/reconnect; these results do not imply live cross-DC qualification. See `PHASE3_FINAL_REPORT.md`.

Direct Go execution loads a private literal `.env`; process variables override it. Compose substitutes `.env` and forwards API credentials/link/expected ID, using a separate `/data` volume. Host data/session paths are deliberately not inherited inside the image. Setup keeps phone entry visible only in the local Terminal, as requested for input verification; OTP and 2FA input remain hidden. Error responses/logs use fixed classifications rather than provider error strings.

Fresh source Compose setup forwards one runtime `DRIVE_SETUP_TOKEN`; adapter and Telegram values can remain unset until web setup. It builds `harbor:local` and preserves the same protected `/data` boundary. Existing published image `1.0.1` and the pinned Dokploy template predate this web/chunk update. They retain their documented terminal flow; source functionality must not be inferred from that tag. See [browser onboarding](WEB_ONBOARDING.md).

Browser upload telemetry separates live sent bytes, acknowledged staged bytes and adapter-committed bytes; resumed speed calculations exclude previously accepted bytes. Managed downloads are bounded to 32 MiB, stream into bounded memory and require exact length and SHA-256 before saving. Larger files use browser-native streaming downloads; Harbor does not claim completion it cannot observe. Managed download pause discards partial browser bytes and restarts safely.

Crash after blob write but before SQLite chunk insertion can leave an unreferenced encrypted blob/message. Resuming remains safe; conservative orphan enumeration/GC is deferred. Do not delete Telegram messages broadly. Default Go build excludes MTProto; `-tags telegram` and default Docker image include it.

## v1.0 release boundary

Version 1.0.0 runtime/source formats remain compatible with Phase 5; no schema/key/chunk migration added. Production Docker builds pin three base image indices. `scripts/release.py` builds an explicit committed Git archive with locked dependencies and epoch-zero timestamps, exports local image/source archives plus manifest/checksums, rejects private source members, and never publishes. Only linux/arm64 qualified. Normal Compose adds metadata; release qualification runs the immutable exported image with the intended Compose runtime controls.

Phase 6 exact-image live Telegram tests cover encrypted multipart/restart/recreation and complete archive-only recovery into a fresh volume. Original authorization is stopped/locked through clone cleanup; restored/host copies never run concurrently. Fresh recovery requires trusted software, archive/password and continued Telegram access, with internal key/config/session paths recovered from the archive. Cross-DC live remains NOT TESTED despite deterministic migration/reference coverage. ## Open-source build boundary

The immutable v1.0.0 release remains historical evidence. Current Docker builds use native `$BUILDPLATFORM` Node/Go stages and cross-compile static Linux AMD64/ARM64 binaries. `HARBOR_VERSION` injects runtime diagnostics and the OCI version. Current source defaults to `1.3.0-dev.1` and accepts stable or numbered `-dev.N`/`-rc.N` build versions; publishing gates still require stable versions. Published Compose image selection remains v1.2.1 until an authorized release. No database, encryption or Telegram format changes are introduced. Runtime images include MIT/third-party notices and corresponding Liberation font source.

Pull-request/main CI has read-only permissions, no Telegram credentials and isolated local-adapter image smoke tests. A separate annotated-stable-tag gate invokes full CI before an owner-gated GHCR job receives package-write permission. Main/PR cannot publish. SBOM/minimal BuildKit provenance use source-only contexts; runtime state/secrets never enter image layers/cache. Remote publishing is NOT TESTED until an approved GitHub run. See [Actions evidence](GITHUB_ACTIONS_REPORT.md) and [publishing guide](GHCR_PUBLISHING_GUIDE.md).
