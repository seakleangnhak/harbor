# Architecture

Last verified: 2026-10-21. Product name: **Harbor** (Telegram Private Drive).

## Process and boundaries

Go/Chi modular monolith serves `/api/v1` and built React SPA on one origin. SQLite in WAL mode stores owner password hash, hashed revocable sessions, nodes and encrypted-content manifests. One DB connection serializes short SQL transactions; network I/O must happen outside transactions. No Redis, external job service, public sharing, signup, or remote URL ingestion. One joined in-process goroutine executes durable SQLite copy jobs.

`internal/api` owns auth, nodes, hierarchy validation, listing, trash, diagnostics and durable copy jobs. `internal/recovery` owns offline encrypted complete archives. `internal/storage` owns persistent upload sessions, chunk metadata, encryption, byte adapters and authenticated random-access readers. `internal/domain` defines shared DTOs; `cmd/drive` owns environment, DB/key lifecycle and adapter selection.

## Frontend workspace

Phase 4 retains React/TanStack Query/Virtual, Radix primitives and native CSS; no new dependency or backend API/schema. Workspace coordinates server queries, metadata optimism/rollback, location preferences and internal clipboard. FileBrowser owns virtual selection/inline editing/internal drag; previews and transfer hook stay separate. Command palette/settings/PDF are lazy. Sidebar state and per-location view/sort preferences are browser-local. Menus are nonmodal; dialogs retain modal focus handling; scrollable PDF/transfer regions are keyboard-focusable. Themes apply before React mount.

Individual browser file copy reads exact authenticated HTTP 206 ranges bounded to the application chunk, verifies total/hash headers and re-uploads through the encrypted engine. Folder-containing selections use persisted server jobs with immutable source metadata snapshots, ancestor pruning, 100 roots/10,000 entries/512 levels and eight unfinished jobs. A single worker stages fresh encrypted content serially using internal `copy:<job>:<entry>` parents. Per-chunk acknowledgements survive restart; indexed reconciliation closes the Begin-to-plan crash window. Internal stages cannot be listed or mutated through user upload routes. Publication inserts the complete hierarchy and completes the job in one metadata transaction after manifest checks. Concurrent source rename/move uses snapshot semantics; destination conflicts fail without partial visibility. Cancellation removes only job-created objects; cleanup failures wait for explicit retry. Original files are never removed by copy failure.

API schema migrations run transactionally with `PRAGMA user_version=1`; unknown future versions fail before migration. Shutdown cancels and joins copy worker before closing DB/transport. Browser copy-job polling refreshes completed locations and exposes persisted progress/retry/cancel; failed stages retain verified chunks. Browser managed file transfers still preserve 1,000 pending and 100 history entries in best-effort localStorage. Uploads need the original file after reload; individual file copies resume verified chunks; managed downloads restart.

Image thumbnails require explicit opt-in and raster size ≤8 MiB; nearby preview strip fetches at most five entries and only raster thumbnails ≤2 MiB. Text fetch/render caps at 256 KiB/2,000 syntax tokens. PDF renders one bounded canvas with demand Range fetching and standard fonts bundled locally. Larger native downloads remain outside managed JS verification above 32 MiB. See Phase 4 reports for browser-only limits and measured bundle/DOM cost.

## Content model

Each file is split into 4 MiB plaintext chunks. Each chunk is sealed independently with AES-256-GCM, random nonce and authenticated upload ID/index. Blob storage receives ciphertext only, with opaque names. Manifest records plaintext chunk SHA-256, size, blob reference and total SHA-256. At most a bounded number of chunks occupy memory; no whole-file buffering. Finalization reads/decrypts every chunk and verifies the whole file before metadata becomes visible. Download uses a seekable chunk reader, verifies each chunk before releasing its bytes and supports HTTP Range for video/PDF. Files are immutable after completion; rename/move changes metadata only.

Phase 3 bounds plaintext input to expected chunk size plus one overflow byte and preallocates its AEAD envelope. Persisted upload geometry is validated before division/allocation (chunk size 1 byte–64 MiB, nonnegative size and bounded chunk count). Readers retain one verified chunk across HTTP preflight/size seeks, then invalidate bytes/index before fetching another; failed fetches cannot reuse stale cache state. Four engine slots bound active chunk operations. Whole-file finalization still holds the API metadata-mutation lock; no concurrency/locking redesign was introduced.

Upload IDs become file IDs. Client stores upload ID and file fingerprint; server persists received indices. Browser reload requires reselecting matching local files (browser security prevents silently reopening file handles). Retrying an identical chunk is idempotent; mismatched replacement is rejected. Finalization is idempotent, and API publishing recovers if process stops between storage completion and node insertion. Zero-byte files are supported. Trashing keeps content intact; permanent deletion durably marks subtree intent before byte removal. A failed/interrupted permanent deletion blocks restore and permits retry after restart.

## Authentication and deployment

Owner password provided by server-side secret file/environment at first boot, then stored as a slow password hash. Login issues random opaque 256-bit cookie; SQLite keeps only token hash and expiration. Session cookie is HttpOnly, SameSite=Strict, Secure when configured. Mutations reject cross-origin requests; Go serves frontend so CORS is unnecessary. Login throttling and body limits constrain abuse. Bind loopback by default; Compose publishes loopback only. Use HTTPS and Secure cookies before any non-loopback deployment.

Content key is a random 32-byte file outside SQLite and Git. Private state requires 0700 directories/0600 secret files; SQLite DB/WAL/SHM are protected before opening. A storage binding records key fingerprint, adapter and Telegram channel ID. Existing missing DB/key/binding fails closed. Non-loopback HTTP requires explicit opt-in or HTTPS cookie policy; Compose keeps host publishing on loopback. `/health` reports process liveness; `/ready` checks SQLite and cached Telegram connection without disclosing identities.

`harbor-recovery` takes the offline process lock, opens SQLite read-only and uses modernc supported Backup/Step/Commit/Serialize APIs into memory, including committed WAL. It writes no plaintext backup snapshot. Version 2 archives encrypt 1 MiB records with scrypt-derived AES-256-GCM, fresh salt, unique sequence nonces and header/order/length AAD; authenticated terminator and encrypted SHA-256 member manifest reject incomplete/corrupt archives. Complete archives include original key, allowlisted explicit runtime configuration, optional matching owner password, valid Telegram session, ordered chunk export, and referenced local blobs where applicable. Cap: 256 MiB metadata, 250,000 members, 1 TiB payload. Restore authenticates into private sibling staging, validates DB/materials, revokes restored web sessions, syncs files and publishes with OS no-replace rename. Original data is untouched. SIGKILL may leave unpublished private staging requiring operator cleanup.

Telegram backups preserve references, not an independent remote-content mirror. Account/channel loss requires an off-provider content copy. Copied MTProto authorization must run serially. `integrity` and `integrity-content` require existing state, audit metadata/content without deletion, and report bounded codes/opaque IDs. Local orphan candidates are review-only; no remote enumeration or automatic garbage collection. See Phase 5 operations and qualification reports.

## Telegram boundary

gotd/td implements MTProto blob storage; encrypted chunk documents map to channel messages. Setup is a server-side terminal flow for phone/code/2FA, never browser credential exchange. Session and channel credentials are configured on server. Setup/startup verify private owned channel and reject auto-delete retention. Owner must keep auto-delete disabled afterward. Flood waits/retries honor context cancellation. Local and Telegram adapters use the same encrypted engine, but data cannot switch backend implicitly. Real Telegram checks require a real dedicated account and are reported separately.

Setup, discovery and startup map typed Telegram, context and network errors to fixed safe categories and guidance. Classification never reads provider error text. Session-file presence does not establish authorization; startup checks account status before channel resolution. Telegram-app/SMS/voice-call OTP and two-step passwords use gotd's auth flow. An optional fixed-method callback supplies delivery guidance without phone/email patterns, codes, URLs or hashes. Unsupported email, caller-ID, Firebase and Fragment methods fail before asking for an ordinary code; no resend is issued.

`telegram-setup-qr` uses gotd's native QR authorization with a three-minute network/approval context deadline and existing blocking local two-step-password callback. A buffered login-update signal prevents losing approval during QR rendering; normal storage clients still disable updates. QR login URLs pass directly to a local Terminal renderer, never HTTP, logs, disk or reports. Rendering uses the already-installed QR dependency with black/white terminal cells and quiet border. Session persistence and target-channel guards are shared with OTP setup.

`USERNAME_OR_CHANNEL_LINK` selects an existing owned private channel by invite or private message link instead of manually supplied access hash. Optional `TELEGRAM_CHANNEL_ID` verifies the resolved target before uploads; CLI normalizes Bot API IDs to positive MTProto IDs. A manual access hash cannot be combined with a link. Invite resolution uses read-only membership checks; no automatic joining/import occurs. Public usernames remain rejected. Startup resolves the selector within the existing authenticated MTProto connection, then checks the numeric channel ID against the immutable storage binding before opening SQLite or the content engine. Access hash remains server-side; no persistent resolver cache or browser exchange exists. Private-message links enumerate eligible normal/archived dialogs; an unrelated retention lookup failure currently blocks resolution rather than accepting an unverified channel.

gotd connection callbacks maintain cached `connecting`, `connected`, `retrying` and `disconnected` states. Authenticated diagnostics expose only state, timestamp and retry count. UI polls every five seconds without probing Telegram on each request. Each chunk operation has a two-minute deadline; application retries stop after six outer attempts, honor flood waits and cancellation, and refresh expired document references. Native gotd retry loops are deadline-bounded and can issue more than six wire requests. Download flood telemetry marks retry before native waiting and avoids duplicate counting. Telegram uploads use 512 KiB parts with a configured two-worker ceiling; gotd's small-file loop sends the default encrypted 4 MiB document sequentially (nine parts instead of 33 at 128 KiB). Interrupted parts restart the current application chunk while committed chunks resume from SQLite. Session replacement syncs file and containing directory.

Document downloads use the existing primary API when the document is in the current datacenter. Exporting authorization to the same datacenter fails with `DC_ID_INVALID`. Other datacenters use native media-only connections, closed after each operation. Both paths retain ciphertext-size limits, bounded context/retry, expired-reference refresh and engine AEAD/SHA-256 verification. Synthetic routing/bounds tests cover both paths; same-DC live retrieval is qualified separately.

gotd's primary invoker handles `FILE_MIGRATE` through cached authorized connections. A selected raw media pool returning `FILE_MIGRATE` now hands the same pending and subsequent reads back to that primary invoker once; native gotd handles target authorization/routing. Context, ciphertext bounds and reference refresh remain unchanged. Deterministic tests verify partial-read continuity, bounded fallback and cancellation. Actual live cross-datacenter placement/migration remains NOT TESTED. Phase 3 separately qualified real Telegram inside Docker, old-file retrieval, container recreation, partial-HTTP-upload SIGKILL and network detach/reconnect; these results do not imply live cross-DC qualification. See `PHASE3_FINAL_REPORT.md`.

Direct Go execution loads a private literal `.env`; process variables override it. Compose substitutes `.env` and forwards API credentials/link/expected ID, using a separate `/data` volume. Host data/session paths are deliberately not inherited inside the image. Setup keeps phone entry visible only in the local Terminal, as requested for input verification; OTP and 2FA input remain hidden. Error responses/logs use fixed classifications rather than provider error strings.

Browser upload telemetry measures acknowledged bytes and excludes persisted bytes from resumed speed calculations. Managed downloads are bounded to 32 MiB, stream into bounded memory and require exact length and SHA-256 before saving. Larger files use browser-native streaming downloads; Harbor does not claim completion it cannot observe. Managed download pause discards partial browser bytes and restarts safely.

Crash after blob write but before SQLite chunk insertion can leave an unreferenced encrypted blob/message. Resuming remains safe; conservative orphan enumeration/GC is deferred. Do not delete Telegram messages broadly. Default Go build excludes MTProto; `-tags telegram` and default Docker image include it.

## v1.0 release boundary

Version 1.0.0 runtime/source formats remain compatible with Phase 5; no schema/key/chunk migration added. Production Docker builds pin three base image indices. `scripts/release.py` builds an explicit committed Git archive with locked dependencies and epoch-zero timestamps, exports local image/source archives plus manifest/checksums, rejects private source members, and never publishes. Only linux/arm64 qualified. Normal Compose adds metadata; release qualification runs the immutable exported image with the intended Compose runtime controls.

Phase 6 exact-image live Telegram tests cover encrypted multipart/restart/recreation and complete archive-only recovery into a fresh volume. Original authorization is stopped/locked through clone cleanup; restored/host copies never run concurrently. Fresh recovery requires trusted software, archive/password and continued Telegram access, with internal key/config/session paths recovered from the archive. Cross-DC live remains NOT TESTED despite deterministic migration/reference coverage. See [Phase 6 acceptance](PHASE6_FINAL_REPORT.md), [release checklist](RELEASE_CHECKLIST.md) and [known limitations](KNOWN_LIMITATIONS.md).

## Open-source build boundary

The immutable v1.0.0 release remains historical evidence. Current Docker builds use native `$BUILDPLATFORM` Node/Go stages and cross-compile static Linux AMD64/ARM64 binaries. `HARBOR_VERSION` accepts a stable version and injects runtime diagnostics and the OCI version; its development default remains 1.0.0. No database, encryption or Telegram format changes are introduced. Runtime images include MIT/third-party notices and corresponding Liberation font source.

Pull-request/main CI has read-only permissions, no Telegram credentials and isolated local-adapter image smoke tests. A separate annotated-stable-tag gate invokes full CI before a protected GHCR job receives package-write permission. Main/PR cannot publish. SBOM/minimal BuildKit provenance use source-only contexts; runtime state/secrets never enter image layers/cache. Remote publishing is NOT TESTED until an approved GitHub run. See [Actions evidence](GITHUB_ACTIONS_REPORT.md) and [publishing guide](GHCR_PUBLISHING_GUIDE.md).
